# 编辑器增量/懒解析 优化评估（rich_text 共享包）

- status: proposed（未实施，待评审）
- updated: 2026-10-14
- 关联：goodhub 增量对话流式渲染；goodshare 交互编辑（后续）
- 结论：**先做方案 A（尾块增量），B（块级 memoize）后续演进，C（逐字符真增量）不做**

---

## 1. 现状与瓶颈定位

`MarkdownSubsetParser.parse()` 当前是**无状态全量解析**：

1. 全文 `split('\n')` + R3 引用定义两遍扫描（每行 1 个正则）；
2. 责任链逐行试 9 个 `_BlockSyntax.canParse`（块级正则，便宜）；
3. 命中块后走 `_parseInlineImpl`（`_extractCode` 双扫描 + `_inlinePattern.allMatches` + 排序 + 节点构造/合并）——**成本大头**。

goodhub 增量对话 = AI 流式追加 token，每次追加触发重渲染 → 重新 `parse` 整篇。
设文档 n 字符、每次追加 k 字符，累计成本 ≈ **O(n²/2k)**。
10KB 文档在流式尾声阶段，单次全量 parse 预估毫秒级~十几毫秒，帧内同步执行有卡顿风险；
且 goodhub 是只读宿主渲染器、每次追加都消费 AST，节流无法完全规避。

利好事实：

- **AST 节点全部不可变**（`final` 字段 + const 构造），块间可安全共享复用——增量天然地基；
- 行内/块正则已是 `static final`（编译缓存已有），无重复编译浪费；
- 围栏内容不做行内解析，`CodeBlock` 重解析仅 join，成本极低。

## 2. 方案对比

| 方案 | 思路 | 复杂度 | 收益 | 风险 |
|---|---|---|---|---|
| A. 尾块增量（有状态 parser） | 检测「纯追加」（`new.startsWith(old)`），只从**最后一个块起始行**起重解析，前面块复用 | 低 | 流式场景单次 O(尾块)，累计≈O(n) | 需正确判定「最后一个块起始」 |
| B. 块级 memoize（分片缓存） | 切块片段→逐片 hash→未变片段复用；变更片段重解析 | 中 | 任意位置编辑（goodshare 交互编辑器也受益） | 切分/缓存管理复杂；hash 成本 |
| C. 逐字符真增量 | 维护行状态机，单行变更局部重算 | 高 | 极致 | 本子集有交叉语法，成本不成比例 |

**推荐：先做 A，B 后续，C 不做。** goodhub 增量对话 ≈ 90%+ 纯追加，A 一条路径吃掉绝大部分收益，改动最小；
A 做成独立有状态类（如 `IncrementalRichTextParser`，`parse(md)` 同签名），零改现有 API，goodshare 全量路径不受影响，灰度易。
B 价值在「文档中间编辑」，goodhub 流式用不到，等 goodshare 编辑侧有性能诉求再做。

## 3. 方案 A 正确性分析（关键边界）

「纯追加不会改写已闭合块」在子集内基本成立（块判定左到右、前瞻 ≤2 行即表格）：

- **开放块**：追加只影响当前未闭合块——开放段落、开放围栏、开放列表（续行吸收）、开放引用；
  从「最后一个块起始行」起重解析即可。
- **R3 引用定义**：全文档两遍。增量路径先探测 `refDefs` 是否空（对话常见为空）→ 空则走快路径；
  非空或本次新增定义 → 回退全量（保守正确）。
- **危险 case 排查**：
  - 段中插入 `# x` 拆段 → 非纯追加，前缀检测失败 → 自动回退全量，安全；
  - 追加 `---` 闭合前面开放段落 → 属「最后一个块起始行」重划，被 A 覆盖；
  - `_isBlockStart` 的 media-link 依赖 `classifyMediaUrl`——行内纯函数，无跨行状态，安全；
  - 必须单测钉死：**列表续行吸收 + 裸待办并入**（陷阱 B 两条特征）尾块重解析与全量逐节点一致。

## 4. 落地切分（待实施）

1. **`IncrementalRichTextParser`（lib 侧，新文件）**：内部持 `lastText/lastBlocks/lastTailStart`；
   `parse()` 前缀检测 + refDefs 空检测 → 命中则复用 `lastBlocks.sublist(0, stableCount)` + 重解析尾块；否则回退全量。
   纯追加快路径内嵌一次 O(n) 尾块起始行回扫（仅块级正则，不行内解析），摊还后仍线性小常数。
2. **差分护栏测试（test 侧）**：随机流式追加序列，断言增量结果与 `MarkdownSubsetParser().parse()` 全量
   **逐节点相等**（借 serialize 往返做相等出口）；重点覆盖列表续行、裸待办、未闭合围栏、表格前瞻、R3。
3. **goodhub 接入**：渲染器把每次对话追加的 `parse` 换成增量实例（一文档一实例），API 不变。

## 5. 验收口径

- 差分：随机追加序列 ≥ 数百轮，增量 ≡ 全量（serialize 后逐字节相等）；
- 性能：10KB 文档流式尾部单次 parse 降至全量 ~5% 内（粗基准观测，不挂硬阈值 CI）；
- 回退：非纯追加 / refDefs 非空 → 同全量（同一函数，天然成立）；
- 现有幂等/降级测试零回归。
